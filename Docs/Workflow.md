# Project Delivery Workflow

This file and `AGENTS.md` are normative for the custom workflow layer. Spec Kit-generated feature artifacts remain authoritative for each feature.

## Authority model

Project constitution/rules govern what the project may do. The pinned official Spec Kit governs overlapping SDD mechanism. A genuine conflict goes to the human decision-maker.

## Default Claude command surface

The scaffold pins Spec Kit and initializes Claude in skills mode by default, so examples use hyphenated commands. Other integrations must use the invocation form actually generated by the pinned Spec Kit.

## New ideas / features

Use bundled `assess` when discovery/go-no-go is useful:

```text
/speckit-assess-intake
-> /speckit-assess-research (when evidence is useful)
-> /speckit-assess-define
-> /speckit-assess-shape
-> /speckit-assess-decide
```

A `go` enters delivery:

```text
/speckit-specify
-> /speckit-clarify
-> HUMAN SPEC APPROVAL
-> /speckit-plan
-> HUMAN PLAN APPROVAL for material technical/public-contract decisions
-> /speckit-tasks
-> /speckit-analyze
-> optional /speckit-checklist
-> TDD RED evidence
-> /speckit-implement
-> bash scripts/verify.sh
-> /speckit-converge
-> repeat implement/verify/converge while convergence tasks remain
-> adversarial review when flagged
-> PR + CI
-> HUMAN REVIEW
-> merge
-> handoff/devlog
```

The bundled `git` extension owns feature branch creation. Default mapping is one Spec Kit feature to one branch/PR. Task issues do not imply task branches.

`spec.md`, `plan.md`, and `tasks.md` are canonical delivery artifacts. GitHub Issues are optional tracking artifacts.

## Bugs

Use the bundled bug workflow:

```text
/speckit-bug-assess -> /speckit-bug-fix -> /speckit-bug-test
```

Escalate to feature SDD when the remediation changes a public/frozen contract or expands beyond a bounded fix.

## Human gates

Human approval is required before:
- committing to build an uncertain/high-impact idea;
- accepting the final feature spec;
- accepting material plan/public API decisions;
- approving stack substitutions;
- triggering Tier 2 security;
- accepting/defering convergence work;
- merging/shipping.

GitHub branch protection, required checks, PR template and CODEOWNERS provide mechanical backing; see `Docs/Repository-Settings.md`.

## TDD evidence

Use `bash scripts/tdd-evidence.sh red ...` after observing the real pre-implementation failure and `green ...` after the implementation passes. Evidence is written under `.sdd/tdd-evidence/` and summarized in the PR. If RED is impractical, record `skip` with rationale.

## Adversarial review

When flagged, use an independent cold-context agent and the provided findings template. Findings are severity-classified P0/P1/P2 and returned to the human. The reviewer does not silently change scope/code.


## Execution reliability

The persistent `/sdd-home` volume is kept across normal shutdown. Use `scripts/dev.* reset-home` only to deliberately recreate container-local identity/auth state or recover from a host uid/gid ownership change. It removes only the volume mounted at `/sdd-home` and must preserve unrelated Compose volumes. Shell checks must avoid early-exit pipelines that can turn producer SIGPIPE into false failure under `pipefail`.
