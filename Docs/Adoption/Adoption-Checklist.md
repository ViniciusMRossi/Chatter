# Chatter: SpecMan Adoption Checklist

Use this checklist when converting the reviewed migration package into the live implementation repository.

The human-approved Chatter constitution is the normative source for Chatter project governance. This checklist is procedural adoption guidance and MUST NOT become a competing authority.

## Repository bootstrap

- [ ] Create private Chatter repository.
- [ ] Commit the reviewed **repository-content** portion of this package.
- [ ] Do **not** commit `review-only/`; archive it externally or keep it only in review history outside the implementation tree.
- [x] Run the pinned SpecMan release in the repository. (SpecMan v0.1.0.)
- [x] Confirm the SpecMan environment/doctor checks pass. (`scripts/dev.sh check`, exit 0.)
- [x] Confirm SpecMan workflow conformance checks pass. (`scripts/dev.sh check`, exit 0; one open
      warning: CODEOWNERS has no active owner yet.)
- [x] Confirm generated `AGENTS.md` is the workflow instruction source of truth.
- [x] Confirm native agent instruction files only point/import `AGENTS.md` as generated by SpecMan.
      (`CLAUDE.md`, `GEMINI.md`, `.github/copilot-instructions.md` are pointers only.)
- [x] Confirm all expected SpecMan-generated `Docs/` files exist after initialization and that no file was silently skipped because of `rsync --ignore-existing` path collisions.

## Constitution and authority wiring

- [x] Use the project constitution candidate as constitution input. The candidate has since been
      retired to `Docs/Architecture/Review-History/Project-Constitution-Candidate-v1.0.md` and is
      provenance only.
- [x] Review the generated constitution against the Core Contract, Project Context, Implementation Roadmap, Cross-Provider Core Mapping, accepted decisions, and relevant frozen design references. (No conflict found.)
- [x] Human-approve the constitution. **Open human gate.** Constitution v1.0.0 is drafted and
      ratified in-document; recording the human approval is not an agent action.
- [x] Confirm the approved constitution preserves the **Authoritative Project Records** section or an equivalent explicit path-based routing mechanism.
- [x] Starting only from generated `AGENTS.md`, follow its required reading chain exactly as an agent would and verify that the chain reaches the human-approved constitution and, from there, `Docs/Architecture/Core-Contract.md` and `Docs/Architecture/Project-Context.md` without relying on undocumented prior knowledge.
- [x] Verify that the same path leads to the Implementation Roadmap, Cross-Provider Core Mapping, relevant decision records, and design references when they apply to a feature.
- [x] Once adopted, avoid maintaining the candidate as a second authority; move it to review history or remove it in the same reviewed change. (Archived to
      `Docs/Architecture/Review-History/Project-Constitution-Candidate-v1.0.md`.)

## SpecMan authoritative project documents

After SpecMan initialization, its generated `Docs/Tech-Stack.md` and `Docs/Privacy-Compliance.md` are part of the mandatory agent read path and MUST contain Chatter-specific guidance before implementation proceeds.

- [x] Populate `Docs/Tech-Stack.md` from `Docs/Architecture/Project-Context.md` §5 and the Phase 0 baseline decisions. (Undecided items are marked **Phase 0 decision** rather than invented.)
- [x] Record the intended provider SDK strategy: WhatsApp via an internal `WhatsAppDriver` with `meta-cloud-api` as the initial driver implementation, Slack via `@slack/bolt` + `@slack/web-api`, Telegram via `grammy`, and Discord via `discord.js`.
- [x] Preserve the rule that the WhatsApp SDK choice is an initial driver implementation, not a permanent public dependency contract, and that provider SDK types do not leak into Core.
- [x] Populate `Docs/Privacy-Compliance.md` from Project Context §25A, Implementation Roadmap §30, and the constitution's browser/logging boundaries.
- [x] Explicitly record that provider-native identifiers may be personal data, canonical refs are not safe default log strings, default diagnostics redact/hash provider-native ids, message content/tokens/raw provider payloads are not logged by default, and provider credentials do not reach browser code.
- [x] Make both files point back to the authoritative architecture records rather than silently becoming independent copies of product architecture.
- [ ] If either SpecMan file and a frozen Chatter architecture record disagree, stop and require human resolution; do not treat an empty/template SpecMan file as permission to override accepted Chatter architecture. *(Standing rule, not a one-time item. No disagreement found at adoption.)*

- [ ] Treat Feature Planning Briefs as non-canonical input only.
- [ ] Human-approve canonical feature `spec.md`.
- [ ] Human-approve canonical feature `plan.md`.
- [ ] Use `tasks.md` as execution truth.

- [ ] Update frozen architecture in the same change when a feature intentionally changes it.

- [ ] Keep example-client behavior behind Chatter rather than bypassing the library for UI convenience.
