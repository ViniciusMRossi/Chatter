# Project Agent Instructions

`AGENTS.md` is the single source of truth for cross-agent operating instructions.
Agent-native files such as `CLAUDE.md`, `GEMINI.md`, and `.github/copilot-instructions.md` are compatibility shims only. They must not define independent project policy.

## Two authority axes

Do not rank tooling above project policy.

### Project rules

`.specify/memory/constitution.md` is authoritative for project/product/engineering non-negotiables.
`Docs/Tech-Stack.md` owns approved implementation tools and substitutions.
`Docs/Privacy-Compliance.md` owns project data-handling rules.
The active Spec Kit assessment/spec/plan/tasks own the current work contract.

### Workflow mechanism

When this workflow overlaps with GitHub Spec Kit on *mechanism* (artifact layout, command lifecycle, branching, bundled extension behavior), the pinned official Spec Kit behavior wins.
Custom workflow code may extend Spec Kit but must not silently fork or duplicate an upstream mechanism.

If project rules and a tool mechanism genuinely conflict, stop and ask the human decision-maker.

## Container-first execution

The development container is the canonical execution surface. Host OS differences are concentrated in bootstrap and must not change project build/test/workflow semantics.

MUST run in the development container:
- Spec Kit/project automation;
- build, lint, typecheck, tests and dependency installation;
- Git operations performed by the agent;
- workflow scripts and project CLIs unless explicitly documented as host-only.

Host-only activities are limited to Docker runtime/bootstrap, IDE/editor UI, browser authentication, and an agent harness when containerizing that harness is impractical. A host agent must delegate project commands through the container. Prefer `scripts/dev.sh exec ...` / `dev.ps1 exec ...` for commands that should share the long-running development environment; use `run` only for deliberate one-shot containers. `reset-home` is destructive and human-invoked when the persistent container HOME must be recreated; it must remove only the volume mounted at `/sdd-home`, never unrelated project volumes.

## Before working

Read:
1. `.specify/memory/constitution.md` if present;
2. `Docs/Tech-Stack.md`;
3. `Docs/Privacy-Compliance.md` when relevant;
4. `Docs/handoff.md`;
5. the active Spec Kit assessment/spec/plan/tasks and relevant prior records.

## Spec Kit ownership

Use official bundled functionality rather than parallel implementations:
- discovery / go-no-go: `assess`;
- bounded bugs: `bug`;
- feature branches: `git`;
- managed Spec Kit context block: `agent-context`, configured to update `AGENTS.md` only;
- feature delivery: core Spec Kit lifecycle.

The pinned default Claude integration uses skills/hyphen invocation (`/speckit-specify`, `/speckit-plan`, etc.). Other integrations must use the invocation form generated by the pinned Spec Kit and pass compatibility checks before work.

## Feature/branch/task relationship

Default unit of delivery: **one Spec Kit feature = one feature branch = one PR**.
Tasks and GitHub issues are execution/tracking units and do not automatically get separate branches. If a task needs an independent branch/PR, the human should decide whether it is actually a separate feature/spec.

## TDD

Test-first is a project discipline with auditable evidence.
For behavior-changing implementation when practical:
1. identify/write the targeted test first;
2. run it and observe a real RED failure;
3. record RED evidence with `bash scripts/tdd-evidence.sh red ...`;
4. implement the minimum change;
5. rerun and record GREEN evidence;
6. refactor while keeping verification green.

If a meaningful RED step is not practical, record a human-reviewable rationale instead of pretending it happened.
Never claim a test was run if it was not.

A community Spec Kit TDD extension exists but is not bundled/first-party and is not installed automatically. If humans approve it after source review, prefer the approved upstream extension over overlapping local TDD mechanics and update this workflow deliberately.

## Feature flow

Follow `Docs/Workflow.md`. `spec.md` is the canonical product contract; GitHub Issues are tracking artifacts.

## Verification

Run `bash scripts/verify.sh` inside the container before review.
After implementation, run the agent-native Spec Kit converge command. If converge appends tasks, they remain in the current feature/PR by default; implement them and rerun converge until converged. Deferral requires explicit human approval and must not leave the approved feature outcome incomplete.

## Stack substitutions

Do not deviate from `Docs/Tech-Stack.md` without human approval and a recorded substitution.

## Privacy and logging

Check `Docs/Privacy-Compliance.md` when personal data may be involved. Do not log secrets, tokens, authorization headers, personal identifiers, or content unless explicitly permitted.

## Security

Tier 1 runs on every PR. Tier 2 is human-triggered only. Tier 2 tooling and credentials are intentionally absent from the development container; agents may recommend Tier 2 but cannot start it from the canonical project environment.

## Adversarial review

If flagged, the human starts an independent cold-context reviewing agent (prefer a separate session/harness). The reviewer receives the approved spec/plan, diff and verification evidence, does not continue the implementing agent's reasoning, does not silently edit code, and writes findings using `.sdd/adversarial-review-template.md` to `specs/<feature>/reviews/adversarial.md`.

## Handoff

Run `bash scripts/handoff.sh` at session boundaries, context exhaustion, and feature completion. `--summary` and `--next-step` are required. Record verification, RED/GREEN evidence, blockers, questions and gotchas. The script archives the previous handoff before an atomic replacement.

## Shell reliability

Under `set -o pipefail`, do not use a producer piped into `grep -q`/`grep -Fq` as an existence check when the producer can receive SIGPIPE. Prefer captured output, file checks, or direct command status APIs.
